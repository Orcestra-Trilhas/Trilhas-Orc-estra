# Unidade IV: Banco de Dados e Modelagem

---

## 1. Visão Geral

Esta unidade cobre a persistência e a organização das informações: modelagem (conceitual, lógica e física), **SQL básico**, **normalização** e **transações (ACID)**.

Ao final, você será capaz de projetar a estrutura de dados de um sistema, escrever as consultas SQL fundamentais e ler o SQL que o Hibernate gera nas unidades seguintes.

## 2. Orientação de Ambiente: H2 Database

!!! note "Banco de Dados em Memória (H2)"
    Nas unidades de Spring, **não instale** PostgreSQL ou MySQL de cara. Usaremos o **H2 Database** (banco em memória). Ele roda junto com a aplicação Java e não exige instalação.

    **Atenção:** por ser em memória, os dados **somem toda vez que a aplicação reinicia**. Isso é esperado em desenvolvimento.

Nesta unidade, para praticar SQL **antes** de ter uma aplicação Spring, use um editor online como o [SQLBolt](https://sqlbolt.com) (lições interativas) ou o [DB Fiddle](https://www.db-fiddle.com). Quando o projeto Spring existir (Unidade VII), você poderá rodar os mesmos comandos no console web do H2.

## 3. Modelagem de Dados

### 4.1 Modelo Conceitual

Etapa mais abstrata, focada em **entender o problema do negócio**, sem tecnologia. Você identifica as **entidades** (ex.: `Usuario`, `Tarefa`, `Tag`) e como se relacionam, geralmente em um **DER (Diagrama Entidade-Relacionamento)**.

### 4.2 Modelo Lógico

Refina o conceitual definindo **atributos, chaves primárias (PK) e chaves estrangeiras (FK)** e as **cardinalidades**:

- **1:1**: um registro se relaciona com no máximo um de outra entidade (ex.: `Usuario` e `Perfil`). A FK fica em um dos lados e é `UNIQUE`.
- **1:N**: um registro se relaciona com vários de outra (ex.: um `Usuario` tem várias `Tarefas`). A FK fica no lado "N" (`tarefas.usuario_id`).
- **N:N**: vários com vários (ex.: `Tarefa` e `Tag`). Resolvido com uma **tabela associativa** (`tarefa_tag`) cuja PK é composta pelas duas FKs.

Ainda é independente do SGBD específico.

### 4.3 Modelo Físico

Tradução do lógico para a **sintaxe real do SGBD**: tipos (`VARCHAR`, `BIGINT`), constraints (`NOT NULL`, `UNIQUE`, `FOREIGN KEY`), índices e o script `CREATE TABLE`. Os tipos mudam entre bancos: por exemplo, `SERIAL` é do PostgreSQL, enquanto no H2 se usa `BIGINT GENERATED BY DEFAULT AS IDENTITY`. **Nesta trilha, o modelo físico é escrito para o H2.**

```sql
CREATE TABLE usuarios (
    id    BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome  VARCHAR(100) NOT NULL,
    email VARCHAR(150) NOT NULL UNIQUE
);

CREATE TABLE tarefas (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    titulo     VARCHAR(150) NOT NULL,
    descricao  VARCHAR(500),
    concluida  BOOLEAN NOT NULL DEFAULT FALSE,
    usuario_id BIGINT NOT NULL,
    CONSTRAINT fk_tarefa_usuario FOREIGN KEY (usuario_id) REFERENCES usuarios (id)
);

CREATE TABLE tags (
    id   BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE tarefa_tag (
    tarefa_id BIGINT NOT NULL,
    tag_id    BIGINT NOT NULL,
    PRIMARY KEY (tarefa_id, tag_id),
    FOREIGN KEY (tarefa_id) REFERENCES tarefas (id),
    FOREIGN KEY (tag_id)    REFERENCES tags (id)
);
```

### 4.4 Herança no Modelo Relacional

Bancos relacionais não têm herança. Para representar `Tarefa` e `TarefaComPrazo` há três estratégias:

| Estratégia | Como fica | Vantagem | Desvantagem |
| :--- | :--- | :--- | :--- |
| **Tabela única** (*single table*) | uma tabela `tarefas` com todas as colunas e uma coluna `tipo` | simples e rápida, sem JOIN | colunas da subclasse ficam `NULL` nas outras linhas |
| **Tabela por classe** (*joined*) | `tarefas` + `tarefas_com_prazo` ligadas por PK/FK | sem colunas nulas, normalizado | exige JOIN |
| **Tabela por classe concreta** | uma tabela completa para cada classe concreta | sem JOIN para uma subclasse | dados repetidos, consultas polimórficas difíceis |

Na trilha, o padrão adotado é **tabela única**. Você justificará a escolha no Mini Projeto 2.

## 4. Normalização

Normalizar é organizar as tabelas para **evitar redundância e anomalias** de atualização.

- **1FN:** cada coluna guarda um valor **atômico** (nada de "tags" = `"estudo,java,urgente"` em uma coluna só) e não há grupos repetidos.
- **2FN:** está na 1FN e todo atributo não-chave depende da **chave inteira** (relevante quando a PK é composta).
- **3FN:** está na 2FN e nenhum atributo não-chave depende de outro atributo não-chave (dependência transitiva). Ex.: não guarde `nome_do_usuario` dentro de `tarefas`, já que ele depende de `usuario_id`.

Regra prática: **um fato em um lugar só**. Se mudar o e-mail de um usuário exigir atualizar várias linhas, a tabela provavelmente não está normalizada.

## 5. SQL Básico

Todo desenvolvedor back-end precisa ler e escrever estes comandos. É o que o Hibernate executa por baixo da JPA.

### 5.1 DML: manipulando dados

```sql
INSERT INTO usuarios (nome, email) VALUES ('João Silva', 'joao@orcestra.com');

UPDATE tarefas SET concluida = TRUE WHERE id = 1;

DELETE FROM tarefas WHERE id = 1;
```

!!! warning "`UPDATE` e `DELETE` sem `WHERE` afetam a tabela inteira."

### 5.2 `SELECT`: consultando

```sql
SELECT titulo, concluida
FROM tarefas
WHERE concluida = FALSE AND titulo LIKE '%java%'
ORDER BY titulo ASC
LIMIT 10;
```

### 5.3 `JOIN`: combinando tabelas

```sql
-- tarefas com o nome do dono (INNER JOIN: só linhas com correspondência)
SELECT t.titulo, u.nome
FROM tarefas t
INNER JOIN usuarios u ON u.id = t.usuario_id;

-- todos os usuários, mesmo sem tarefas (LEFT JOIN)
SELECT u.nome, t.titulo
FROM usuarios u
LEFT JOIN tarefas t ON t.usuario_id = u.id;
```

### 5.4 Agregação: `COUNT`, `GROUP BY`, `HAVING`

```sql
SELECT u.nome, COUNT(t.id) AS total, SUM(CASE WHEN t.concluida THEN 1 ELSE 0 END) AS concluidas
FROM usuarios u
LEFT JOIN tarefas t ON t.usuario_id = u.id
GROUP BY u.nome
HAVING COUNT(t.id) > 0;
```

`WHERE` filtra linhas **antes** de agrupar; `HAVING` filtra os **grupos** depois.

### 5.5 Índices

Um **índice** acelera consultas por uma coluna (como o índice remissivo de um livro), ao custo de espaço e de escritas mais lentas. PKs e colunas `UNIQUE` já são indexadas automaticamente. Crie índices em colunas muito usadas em `WHERE`/`JOIN` (ex.: FKs):

```sql
CREATE INDEX idx_tarefas_usuario ON tarefas (usuario_id);
```

## 6. Transações e ACID

Uma **transação** agrupa operações que devem acontecer **todas ou nenhuma**. Exemplo clássico: transferir dinheiro (debitar A e creditar B). Se o crédito falhar, o débito deve ser desfeito (`ROLLBACK`).

```sql
BEGIN;
UPDATE contas SET saldo = saldo - 100 WHERE id = 1;
UPDATE contas SET saldo = saldo + 100 WHERE id = 2;
COMMIT;   -- ou ROLLBACK; se algo falhou
```

As garantias de uma transação são resumidas por **ACID**:

- **A**tomicidade: tudo ou nada.
- **C**onsistência: o banco sai de um estado válido para outro estado válido (constraints respeitadas).
- **I**solamento: transações simultâneas não enxergam os resultados parciais umas das outras.
- **D**urabilidade: depois do `COMMIT`, o dado persiste mesmo se o sistema cair.

Na Unidade VII, a anotação `@Transactional` do Spring é a forma de pedir exatamente isso.

## 7. Indo para um Banco Real (para saber mais)

O H2 é para aprender e testar. Em projetos reais da empresa você provavelmente encontrará **PostgreSQL** ou **MySQL**, normalmente rodando em **Docker** e com o esquema versionado por uma ferramenta de **migrations** (como Flyway ou Liquibase), em vez de o Hibernate criar as tabelas sozinho. Esses temas estão fora do escopo desta trilha, mas vale pesquisá-los depois do projeto final.
